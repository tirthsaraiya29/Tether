THE POWER USER GUIDE

What’s actually happening when Tether connects?

A practical tour of the moving parts behind Tether: how your phone finds your computer, how the two devices learn to trust each other, what happens when you tap Unlock, and where your data goes. No source-code knowledge required.

01 · THE BIG PICTURE

Two devices. One direct relationship.

Tether is built around a simple idea: your Android phone can act as a trusted companion for your computer. The phone and computer communicate across your local network instead of sending commands through a Tether cloud service.

1. Your phoneHolds its device identity and the Tether app you use to approve actions.
2. Your Wi-Fi / LANCarries discovery messages and the encrypted connection between your own devices.
3. Your computerRuns Tether background components that receive approved requests and hand work to the right Windows session.
What “local-first” means here

The normal phone-to-PC control path is designed to stay on your local network. Tether’s website and GitHub are used to distribute information and releases; they are not required as a cloud relay for the local control connection.

What runs on each side?

Android companion

Finds the computer, manages pairing and trust, stores the phone’s cryptographic identity using Android Keystore, and provides controls such as unlock, lock and trackpad input.

Windows background service

Listens for local connections, checks device identity and permissions, routes requests, and coordinates with the active desktop session.

Windows session helper

Runs in the interactive user session for work that needs access to the actual desktop, such as delivering mouse and keyboard input.

Windows sign-in integration

A native Windows Credential Provider adds Tether’s phone-assisted sign-in option to the Windows sign-in experience.

02 · DISCOVERY

How your phone finds your PC

When both devices are on a supported local network, Tether uses local discovery rather than asking a remote server where your computer is.

  • mDNS: the computer advertises a service named _tether._tcp. Nearby devices can discover it on the local network (mDNS uses UDP port 5353).
  • UDP discovery: Tether also has a UDP broadcast discovery path on port 37124.
  • Direct connection: after discovery, the phone connects to the computer’s control listener on TCP port 37123.

Discovery is like seeing a name on the local network directory. It is not proof that the discovered computer is trusted. Trust is checked separately during the connection and pairing process.

Network note

Both devices need to be able to reach each other. Guest Wi-Fi isolation, restrictive firewalls, VPN routing, or different network segments can prevent discovery or direct communication. A phone hotspot is not a supported assumption; results depend on how that hotspot handles local peer traffic.

03 · PAIRING & TRUST

Pairing is how the devices learn who to trust

The first connection is a deliberate setup step. Tether creates a device identity for the phone, exchanges public-key information, and asks you to confirm that you are pairing the devices you intended to pair.

Phone creates identityAndroid Keystore holds an EC P-256 identity key pair. Private-key operations are handled by the platform keystore.
Devices exchange public keysThe handshake includes device identity information and fresh values used to bind the exchange together.
You verify the pairingA short-lived six-digit pairing code and displayed fingerprint help you confirm the intended devices.
Trust is savedThe public identity is pinned so later connections can be checked against the device already approved.

What is a fingerprint?

A fingerprint is a short representation of a public key, calculated using a cryptographic hash. It gives you a practical way to compare device identities without comparing a long block of key data.

Where is trust stored?

  • On Android: the phone identity key is kept in Android Keystore. The paired computer’s public key is stored in the app’s protected storage, encrypted using an Android Keystore-backed AES-GCM key.
  • On Windows: the trusted phone public-key records are stored under the shared Tether data directory. The implementation uses Windows DPAPI protection and applies filesystem access controls to the trust store.

Trust can be removed. Forgetting a paired device removes its pinned identity from the relevant trust store, so it should no longer be accepted as the same previously approved device.

04 · THE LIVE CONNECTION

What protects the conversation?

After discovery, Tether opens a direct TCP connection. The control listener is configured for TLS 1.3. In plain English, TLS gives the connection encryption in transit and helps the devices establish a protected channel before exchanging application messages.

Encryption in transit

Network traffic on the control connection is protected by TLS 1.3 rather than sent as readable commands over Wi-Fi.

Device identity

Tether’s pairing and pinned-key checks provide an additional device-level trust decision beyond simply being on the same Wi-Fi.

Separate jobs

The background service handles network work; the interactive helper handles desktop work that belongs inside the logged-in session.

05 · WHEN YOU TAP A BUTTON

How the main features work

Phone-assisted Windows unlock

The Windows Credential Provider is a native component that participates in the Windows sign-in UI. Tether’s provider presents the phone-assisted sign-in flow. The Windows service coordinates with the phone connection and trust state; the provider and service exchange state through local inter-process communication. Windows remains responsible for the actual logon process.

Remote trackpad

Your phone sends compact input events for cursor movement, clicks, scrolling and supported keyboard input. The Windows service forwards those events to a helper running in the interactive desktop session. That helper uses the Windows input APIs to deliver them to the desktop. This separation matters because a Windows service runs in the background service environment, not inside your visible desktop.

Locking the PC

A lock request is routed through the trusted connection to the Windows-side command handler, which asks Windows to lock the workstation. The request is not a magic remote power switch: the PC must be running, reachable, and able to process it.

File transfer

File transfer is implemented as a separate service from the main control listener. It has its own authorization/token handling and transfer limits. Treat transfer availability and platform parity as release-dependent; check the current release notes rather than assuming every build has the same transfer experience.

Why the service and helper are separate

Windows isolates background services from logged-in desktop sessions. Tether uses a service for always-on network and trust responsibilities, then a session helper for tasks that need access to the user's interactive desktop. A local IPC bridge connects those pieces.

06 · SECURITY BOUNDARIES

What Tether tries to protect—and what it cannot promise

Tether combines several layers: encrypted transport, device identity, explicit pairing, protected key storage, trust revocation, and separation between privileged background work and desktop-session work.

  • Local network access alone is not intended to grant trusted-device status.
  • Private identity keys are designed to remain in Android Keystore rather than being exported as ordinary app files.
  • Windows trust data is protected with platform facilities and filesystem permissions.
  • The control listener includes connection limits and per-IP rate limiting to reduce resource abuse.
  • Windows desktop input is handled in the interactive session rather than pretending a service runs on the user’s desktop.
Important: security claims have limits

Tether is under active development and has not had an independent security audit. Hardware-backed key storage depends on the phone’s hardware and Android implementation. Local networking does not make a device automatically safe. Keep your normal Windows sign-in and recovery options available, use a trusted network, and do not rely on a beta build as your only way into an important machine.

07 · CURRENT STATUS

What to expect today

Tether is actively developed across Android, Windows and Linux. The Windows sign-in integration and Android companion are substantial parts of the current project. Linux support is being developed separately and should be treated according to the status of the specific release you install.

Works as a concept today

Local discovery, direct encrypted control transport, device pairing and trust, Windows-side service architecture, and Android companion workflows are present in the codebase.

Check the release before relying on it

Feature availability, file-transfer support, platform parity and installer maturity can differ between builds. The repository README and release notes are the source of truth.
