01 · SYSTEM ARCHITECTURE

Process boundaries are a core design decision

Tether is a multi-process, multi-platform system. On Windows, the network-facing service runs independently of the interactive desktop. A session helper runs where desktop input and user-session APIs are available. The native Credential Provider participates in Windows sign-in. Android is the companion and trust-bearing endpoint.

Android app (Kotlin / Android Keystore) │ │ local discovery → TCP + TLS 1.3 ▼ Tether.CommunicationService (.NET / Windows Service) ├── Discovery + TCP listener ├── PairingManager + TrustStore ├── PacketRouter + CapabilityManager ├── SessionManager + InputForwarder ├── Panic / Trust / Enforcement engines ├── FileTransferServer (separate listener) └── Named-pipe IPC │ ▼ Tether.SessionHelper (interactive user session) ├── Input injection ├── Session-bound desktop operations └── Other user-session capabilities Windows LogonUI └── TetherCredentialProvider.dll (native COM provider) ↕ local service coordination

Why not one process?

  • Service lifetime: network discovery and device trust should not depend on a desktop UI window remaining open.
  • Session isolation: Windows services run in Session 0; desktop input and interactive UI work belong to a logged-in user session.
  • Native sign-in integration: Windows Credential Providers are COM-based native components loaded by the Windows sign-in infrastructure.
  • Failure containment: separating components gives the system clearer ownership boundaries, though it also introduces IPC and lifecycle complexity.

02 · NETWORKING & TRANSPORT

Discovery is not trust; transport is not pairing

Discovery metadata

The Windows MdnsAdvertiser publishes a service profile with protocol version, device ID, display name, capability metadata, a PQC flag, and an optional file-transfer port. Discovery data helps the client find and classify a host. It must not be treated as authenticated identity; the subsequent handshake and trust checks do that work.

TCP accept-path guardrails

TetherTcpServer accepts on a dual-mode IPv6 listener and applies bounded connection controls, including a global active-session ceiling, per-IP concurrency ceiling, per-IP connection-rate limit, and bounded IP tracking. The current constants in the implementation are 16 concurrent sessions, 5 per IP, and 60 new connections per IP per minute, with tracking bounded to 1,024 IPs.

Protocol framing and routing

The transport/session layer reads framed messages and passes decoded application messages to PacketRouter. The router dispatches message types such as ping/pong, handshake proof, command execution, input events, and file-transfer authorization requests to their owning services. Request IDs are normalized before routing. Keep framing, authentication and command authorization as distinct layers when changing this path.

03 · PAIRING PROTOCOL

First-contact flow and subsequent reconnects

The Android TetherPairingManager and Windows PairingManager implement the device handshake and first-pairing workflow. The current protocol version is declared as 2.0.

1 · Client identityAndroid obtains its EC public identity key and computes a SHA-256 fingerprint.
2 · Fresh handshake dataClient/server nonces and public-key material are combined into a transcript.
3 · Existing pin checkA previously pinned server key is compared with the presented identity; mismatch is a distinct result.
4 · Pairing approvalFor first pairing, Windows creates a pending request and a cryptographically random six-digit code.
5 · Verify & persistThe confirmation flow validates the request and records the peer public key as trusted.

Implementation details visible in source

  • Android identity aliases include TetherIdentityKey_v2, with legacy v1 cleanup logic.
  • The identity algorithm is EC P-256 with SHA-256 ECDSA signatures. StrongBox is attempted where supported; availability is device-dependent.
  • The Android implementation builds a length-prefixed handshake transcript containing nonces and both public keys, then hashes transcript material with SHA-512 in relevant proof flows.
  • Windows pending pairing requests expire after 120 seconds. The pairing manager caps failed attempts at three and bounds pending requests.
  • The pairing PIN is generated using a cryptographically secure random-number generator. The service deliberately avoids publishing the cleartext PIN on its in-process event bus.
Protocol caution

Do not describe this as post-quantum secure. The current Windows mDNS advertisement explicitly reports pqc=false in the inspected implementation path. A metadata field or roadmap item is not proof of a deployed PQC handshake.

04 · TRUST & KEY STORAGE

Public-key pinning and platform-backed storage

Android side

ProductionSecurityEngine provisions the EC identity in AndroidKeyStore. The private key is not intended to be exported to app-managed files. The code requires user authentication for key use and defines a five-minute authorization validity window for supported background signing flows. StrongBox is attempted when available, with platform fallback logic.

The paired Windows public key is stored as encrypted app preference data. The encryption key is managed in Android Keystore; the inspected implementation uses AES-GCM parameters and distinguishes unprovisioned, present, and corrupted pinned-key states.

Windows side

TrustStore stores trusted phone public-key records in %ProgramData%\Tether\trust.json. Fingerprints are SHA-256 over the decoded SubjectPublicKeyInfo bytes. The implementation uses DPAPI protection, access-control checks, and reparse-point/ownership handling around the data directory and file. Trust operations include add/update, lookup, touch, remove and clear.

Revocation and state

Trust revocation must be considered across all active sessions and cached state, not only the persisted JSON record. When modifying trust flows, inspect TrustStateManager, TrustStoreProviderBridge, the Android pinned-key cache, and session teardown together.

05 · WINDOWS INTEGRATION

Credential Provider, service and session helper

Credential Provider

TetherCredentialProvider.dll is a native C++ COM implementation of the Windows Credential Provider interfaces. The provider supports the logon, unlock-workstation and CredUI usage scenarios in the inspected implementation; password-change and PLAP scenarios return E_NOTIMPL. Its job is to expose the sign-in tile and coordinate the credential flow—not to own the network stack.

The provider must be treated as a critical sign-in surface. Preserve a reliable fallback sign-in route during development and installer testing. Test LogonUI lifecycle events, credential enumeration/re-enumeration, cancellation, user switching, lock/unlock, service restarts and failure recovery.

Communication service

Tether.CommunicationService is the Windows hosted service and composition root. Program.cs registers discovery, transport, pairing, trust, session, capability, IPC, panic and file-transfer components through dependency injection. When running as a Windows service, it configures the Windows service host and Event Log integration.

Session helper & IPC

Tether.SessionHelper runs in the interactive session. The service launches/coordinates the helper and relays messages over named-pipe IPC. InputInjector owns a dedicated worker thread, attaches to the interactive desktop, and dispatches Windows SendInput events. It uses a bounded queue and tracks held keys/buttons so shutdown and error paths can release state safely.

Contributor rule

Do not move desktop-only work into the service just because it is convenient. First identify the required Windows session, integrity level, desktop/window-station access and IPC trust boundary.

06 · ANDROID CLIENT

Service lifecycle, discovery and security engine

The Android companion is a Kotlin application. TetherLanService owns long-lived LAN connectivity and exposes explicit transport states such as DISCOVERING, CONNECTING, TLS_HANDSHAKE, AUTHENTICATING, PAIRING_REQUIRED, AUTHENTICATED, READY and FAILED.

TetherPairingManager handles the identity handshake and maps outcomes into typed results: authenticated, pairing pending, denied, key mismatch, invalid PIN and error. ProductionSecurityEngine owns Android Keystore identity creation, signing, pinned-key encryption and biometric/user-auth integration.

Areas to preserve when changing Android networking

  • Make transport state transitions explicit and observable; avoid treating “socket connected” as “authenticated”.
  • Keep cryptographic operations behind the security engine rather than spreading raw key handling through UI/service code.
  • Handle key invalidation/corruption as a security state requiring deliberate recovery, not as a silent empty trust store.
  • Test reconnect, process death, network handoff, permission changes, Doze/background restrictions and biometric authorization expiry.

07 · FILE TRANSFER

A separate data plane with its own authorization

The Windows implementation registers FileTransferServer as a hosted service. It uses a separate listener from the control TCP server and has dedicated token storage and authorization middleware. The code defines a maximum upload size of 4 GiB per transfer, a 64 KiB JSON control-payload limit, a 250 MiB free-space safety buffer, and a maximum of four concurrent transfers.

Remote operations are correlated to expected session IDs, device fingerprints and operation names. Keep those bindings intact: a valid transfer token should not become a generic authorization to perform unrelated control operations.

File transfer is a sensitive filesystem boundary. Preserve path canonicalization, reserved-name checks, blocked-directory protections, bounded request bodies, disk-space checks, cancellation, cleanup and safe handling of partial files. Test symlinks/reparse points and Windows path edge cases on the actual target platform.

Do not assume transport parity

The control channel and file-transfer channel are distinct. Confirm the current Android/Linux/Windows transfer protocol and release compatibility before documenting or depending on a specific wire protocol or port.

08 · LINUX IMPLEMENTATION

Linux is a native platform path, not a Windows shim

The repository contains a dedicated Tether.LinuxDaemon, Linux pairing and trust stores, a file-transfer server, PAM integration assets, systemd installer units and uinput configuration. The Linux sign-in path uses PAM rather than the Windows Credential Provider.

The Linux installer configures the daemon, PAM module, udev rules for input, firewall rules and a systemd service. Exact support depends on distribution, PAM stack layout, desktop/session manager and packaging state. Read the Linux installer and release notes before assuming a distribution is supported.

Linux files worth reading

  • services/communication-service/Tether.LinuxDaemon/ — daemon, pairing, trust and transfer implementation.
  • installer/linux/install.sh and uninstall.sh — lifecycle and system integration.
  • installer/linux/selinux/ — SELinux policy source.
  • tests/Tether.LinuxTests/ — Linux-specific test coverage.

Threat boundaries contributors should understand

Project status

Tether is active development software and has not been independently security audited. The presence of TLS, Android Keystore, DPAPI, ACLs or rate limits is not a certification or proof that the complete system is secure. Treat every trust boundary as something to verify through tests and review.

11 · BUILDING & CONTRIBUTING

Make changes with the boundary in mind

Use the repository README as the authoritative source for current SDK versions, prerequisites, build commands and installer instructions. This page is an architecture map, not a substitute for the build scripts or CI configuration.

Before changing a subsystem

  • Trace the complete request path from Android UI/service through transport, routing, service/helper IPC and back.
  • Identify the trust state required for the operation. “Connected” and “trusted” must remain separate states.
  • Check both sides of every wire-format change. Shared DTOs and Kotlin/C# protocol definitions must stay compatible.
  • Add tests for malformed frames, oversized payloads, disconnects, retries, duplicate requests, cancellation and restart behavior.
  • For Windows sign-in or installer work, preserve recovery paths and test on a disposable VM or machine snapshot.
  • For file transfer, test traversal, reparse points, reserved names, disk exhaustion, cancellation and partial-file cleanup.
  • Never log private keys, PINs, bearer tokens, sensitive file paths or full authentication payloads.
